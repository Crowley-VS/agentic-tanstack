# 0007 — Drizzle, and Postgres 18 in Docker everywhere

- **Status:** accepted (2026-09-29; replaces the PGlite design after spike S2 failed, confirmed by
  spike S2b)
- **Applies to:** `packages/db`, `docker-compose.yml`, `tools/dev-ports.mjs`, every `needs-db` project

## Context

Production runs managed Postgres 18 (Railway). Development, tests and e2e should run the same
engine, so a query that works locally works deployed. Agents work in parallel git worktrees, so
each checkout needs a database nobody else writes to, and each test file one its neighbours cannot
disturb. Schema changes must be reviewable migrations, generated from typed TypeScript.

The first plan used **PGlite** (Postgres compiled to WebAssembly) for development and tests: no
Docker, a database per worktree for free. Spike S2 tested `pglite-server` with several connections
and **failed**: its connection multiplexer can run one connection's SQL with another connection's
parameters, and all connections share one session (transactions and settings leak between them).
The fallback, PGlite in-process inside the API with a single connection, a process lock, and
drizzle-kit's `migrate` and `studio` usable only while the app was stopped, worked but added rules
and a second driver. So the database became Docker Postgres everywhere.

## Decision

- **Drizzle** (`drizzle-orm` and `drizzle-kit` 1.0.0-rc.4, pinned exactly): the schema in
  `packages/db/src/schema`, relations in `relations.ts`, migrations generated by drizzle-kit with a
  name (`pnpm db:generate <what>`), reviewed and committed, applied on every deploy. Never pushed.
- **One driver everywhere**: `drizzle-orm/node-postgres` with `pg`, in development, tests, e2e and
  production.
- **Postgres 18 in Docker** for everything local: `postgres:18.6-trixie` (glibc, so text sorts as
  on managed Postgres; Alpine's musl sorts differently), one compose project per checkout, on that
  checkout's port (`tools/dev-ports.mjs`: fixed defaults in the primary checkout, a block of its
  own in each worktree). `pnpm db:up` starts it and is a fast no-op when it already answers; every
  target that needs it depends on it.
- **Databases on that server**: `app` for development, `e2e` recreated and seeded by each e2e run,
  and for tests a migrated `test_template` that each test file clones into a database of its own
  (`testDb()` from `@acme/db/testing`).
- **Development-only server flags** (`fsync`, `synchronous_commit` and `full_page_writes` off),
  bound to `127.0.0.1`.
- **Writes and domain errors in `packages/core`**; reads through Drizzle's relational queries (in
  the API, the Pothos Drizzle plugin: [0005](0005-graphql-yoga-pothos.md)).

## Consequences

- **Docker Engine with Compose v2 is required**, and must be running, for `pnpm dev` and for
  `pnpm check` (the database tests). Sessions without Docker can run every check but those:
  `pnpm nx affected -t lint eslint typecheck build`, then
  `pnpm nx affected -t test --exclude=tag:needs-db`.
- Isolation is real: two worktrees never share a server, and two test files never share a
  database. Measured in S2b: a warm start check takes about 10 ms (no Docker call), a cold
  `up --wait` about 1 s, a test database clone about 9 ms; idle memory about 35 MiB.
- Each checkout leaves a container and a volume behind until `pnpm teardown` (container) or
  `pnpm prune:orphans` (a deleted worktree's): [local-resources.md](../local-resources.md).
- drizzle-kit's `migrate` and `studio` work normally against `DATABASE_URL`, with no "only while
  stopped" rule.
- Learned in S2b: drop test databases with a plain `DROP DATABASE`, not `WITH (FORCE)` (a closing
  connection then surfaces as an unhandled `57P01`); always attach `pool.on('error')`; local URLs
  carry no `sslmode`.
- Drizzle 1.0 is a release candidate: its version and `@pothos/plugin-drizzle` move together, on
  purpose.

## Alternatives considered

- **PGlite** (`pglite-server`, then in-process): dropped, as above.
- **Prisma**: a schema language of its own and a generate step; Drizzle's schema is TypeScript and
  its queries read like SQL.
- **SQLite in development**: differs from production Postgres in types, constraints and SQL.
- **A shared cloud database for development**: no isolation between agents or worktrees, and a
  network dependency for every test.
- **Testcontainers**: a container per test run; one long-lived server per checkout with cloned
  databases is faster and shares the dev server's lifecycle.
