# 0002 — Nx as the monorepo tool, with its agent configuration

- **Status:** accepted (2026-09-29)
- **Applies to:** the workspace (`nx.json`, every `package.json#nx`), `CLAUDE.md`, `pnpm check`

## Context

An agent in a monorepo has to answer, before every change: what exists, where does this code
belong, what depends on it, and what must I re-run to prove the change. Without a tool that knows,
it greps, guesses ownership, misses what a change breaks and re-runs everything to be safe. The
template also needs architecture rules (which package may import which) that fail a check rather
than live in a document.

## Decision

- **Nx 23** (`nx` and every `@nx/*` plugin pinned exactly, 23.2.1) in its TypeScript-solution
  mode. Each project's name, tags and targets live in its `package.json#nx`; internal packages are
  not built but resolved from source through the `@acme/source` export condition; `nx sync` keeps
  the tsconfig project references in step (`pnpm check` runs `nx sync:check`).
- **Targets are inferred by plugins** (`nx.json`): `@nx/js/typescript` (typecheck), `@nx/vitest`
  (test), `@nx/oxlint` (lint), `@nx/eslint` (eslint), `@nx/playwright` (e2e, and `e2e-ci` per spec
  file). Hand-written targets cover the rest (codegen, print-schema, the database, the images).
- **The project graph is the first tool agents reach for**: `pnpm nx show projects --affected`,
  `pnpm nx show project <name> --json` (`AGENTS.md`, "How to navigate").
- **`pnpm check` runs on the affected projects only** (`nx affected`; `--all` for every project),
  and the cache replays tasks whose inputs did not change; CI checks that the generators and
  builds replay from it on a second run.
- **Tags as architecture**: `scope:*` and `type:*` tags, enforced by
  `@nx/enforce-module-boundaries` (`eslint.config.mjs`; [architecture.md](../architecture.md)).
- **Nx's own agent configuration** comes from `nx configure-ai-agents`: the Nx block in
  `CLAUDE.md`, and the settings and `.gitignore` lines it writes; the `nx@nx-claude-plugins` plugin
  (Nx's skills and MCP server) is on for the project. A human runs it
  (`pnpm agents:nx`) and commits the result; agents are denied running it, and `pnpm check` fails
  when what it would write differs from the committed files. `NX_USE_LOCAL=true` in the agent
  settings keeps Nx from installing `nx@latest` into the temp directory.

## Consequences

- Agents verify a change by running only what it affects, in seconds to minutes, and the same
  command runs in CI.
- Boundary rules are lint errors with a file and a line, not review comments.
- ESLint's boundary rule needs the project graph: lint runs only through Nx (`pnpm nx run
<project>:eslint`); run alone, the rule silently checks nothing ([0010](0010-oxlint-oxfmt.md)).
- Nx upgrades touch many packages at once and can rewrite configuration: they go through the
  `nx-upgrade` skill (`nx migrate`), not a dependency bot.
- An Nx daemon runs per checkout; `pnpm teardown` stops it ([local-resources.md](../local-resources.md)).
- The Nx MCP server in the plugin starts with `npx nx-mcp@latest`, outside this repo's pins
  ([agents.md](../agents.md)).

## Alternatives considered

- **Turborepo**: lighter and fast, but a task runner over package scripts: less graph detail
  (no project tags or boundary rule, no inferred targets) and no agent tooling of its own.
- **moon**: strong for polyglot repositories, with a smaller ecosystem of plugins for this stack.
- **pnpm workspaces alone**: no affected runs, no cache, no boundaries; every check would run on
  everything.
